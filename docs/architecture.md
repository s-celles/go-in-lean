# Architecture and verification pipeline

## Components

```
go-in-lean/
├── GoInLean/
│   ├── Semantics/Int.lean        Go integer semantics as BitVec operations (+ panics)
│   ├── Semantics/Validation.lean  executable checks of those primitives against Go behaviour
│   ├── Semantics/BitSpec.lean     naive, unrolled oracle definitions (len, ctz, popcount, …)
│   ├── Stdlib/BitsTables.lean     GENERATED from Go sources: lookup tables + bit-blastable twins
│   ├── Stdlib/Bits.lean           line-by-line transliteration of src/math/bits/bits.go
│   ├── Properties/Bits.lean       specifications and proofs (one theorem per manifest entry)
│   ├── Semantics/Slice.lean       backing-array slice model (heap + descriptors, StateT/Except monad)
│   ├── Stdlib/SlicesArr.lean      slices.Insert/Delete/Replace/Reverse with aliasing, transliterated
│   ├── Stdlib/Slices.lean         list model: Compact, Index, Contains, sort.Search
│   ├── Compiler/GenericRules.lean hand-modelled SSA rewrite rules (Phase 6)
│   ├── Compiler/OpSem.lean        semantics of the generic SSA ops used by constant folding
│   ├── Compiler/GeneratedFolds.lean GENERATED by scripts/rules_to_lean.py from generic.rules
│   ├── Audit.lean                 `lake exe audit`: axiom audit of every theorem in namespace Go
│   ├── CheckVectors.lean          `lake exe checkvectors`: Lean models vs Go-produced vectors (math/bits)
│   ├── SliceSearch.lean           `lake exe slicesearch N`: bounded exhaustive slices model vs spec
│   └── CheckSlices.lean           `lake exe checkslices`: slices model vs real Go on every configuration
├── mutants/                       deliberately wrong models (not built by `lake build`)
├── go/
│   ├── tests/                     property tests on the real stdlib (oracle: math/big, bit folds)
│   ├── tests/vectors/             generator of the differential vectors
│   ├── reference/                 Go twins of the mutants
│   └── reproducers/               GENERATED Go tests from Lean counterexamples
├── targets/properties.yaml        manifest: id, source, spec, theorem, oracle, status, history
├── scripts/                       check.sh (everything), gen_bits_tables.py, validate_manifest.py,
│                                  mutation_test.py (counterexample → Go reproducer)
├── findings/                      one directory per finding that reached Go reproduction
└── docs/                          prior-art, semantic-boundary, this file, compiler feasibility, report
```

## Pipeline (Phase 4 stages)

| Stage | Where | Mechanism |
|---|---|---|
| A. Source acquisition | `docs/semantic-boundary.md`, `scripts/gen_bits_tables.py` | GOROOT of the pinned toolchain; sha256 of each modelled file recorded; tables regenerated and diffed in CI |
| B. Formal modelling | `GoInLean/Stdlib/*.lean` | transliteration, fully parenthesised (A6), Go line numbers in comments |
| C. Property formulation | `GoInLean/Properties/*.lean`, `targets/properties.yaml` | one theorem per documented promise; oracle definitions independent of the implementation (`BitSpec`); ambiguity recorded in the manifest |
| D. Proof attempts | `lake build` | `decide` (kernel) for tables and small widths, `bv_decide` for fixed-width identities, `omega`/`simp` for Nat glue; no `sorry`, no `native_decide` (source scan) |
| E. Counterexample exploration | `bv_decide` counterexamples; `decide`-checked refutations; `lake exe slicesearch` bounded exhaustive search | a failed proof is classified: SAT timeout → `inconclusive`; "potentially spurious" → unsupported model shape → `inconclusive`; concrete assignment → `counterexample_in_model`; a search mismatch is a `counterexample_in_model` candidate that must then replay in Go |
| F. Go reproduction | `scripts/mutation_test.py`, `go/reproducers/` | assignment parsed into a generated `_test.go`; run on the pinned toolchain against the mutant *and* the real function |
| G. Classification | `targets/properties.yaml` | status + chronological history; `validate_manifest.py` enforces that each status has the evidence it requires |

## Trusted computing base

* **Lean kernel** (plus Lean's standard axioms `propext`, `Quot.sound`,
  `Classical.choice`): everything tagged `kernel` in `lake exe audit`.
* **`bv_decide`**: the SAT solver's answer is not trusted; the LRAT
  certificate is checked by a checker proven correct in Lean but *executed
  through the Lean compiler*. In Lean 4.35 the kernel admits that native
  evaluation through a per-theorem axiom named
  `<theorem>._native.bv_decide.ax_…` (the role `Lean.ofReduceBool` played
  before 4.35). Theorems tagged `bv_decide` therefore trust the compiler and
  the native checker. This is the deliberate deviation from
  julia-in-lean (which bans `bv_decide`); without it the 64-bit bit-trick
  identities (`OnesCount64`, `TrailingZeros64`, `Reverse64`, carry/borrow
  formulas) would be out of reach. `native_decide` would introduce an axiom of
  the same kind (`._native.decide…`); the audit only accepts the
  `._native.bv_decide.` form, and the source scan in `scripts/check.sh`
  bans `native_decide` as a second line of defence.
* **Model fidelity** is *not* proved. The link between `GoInLean.Stdlib.Bits`
  and Go is (i) human-readable transliteration with line references, (ii)
  generated tables with recorded checksums, (iii) differential vectors on
  47k inputs produced by the real toolchain, (iv) Go property tests with
  `math/big` as oracle. A `proved_in_model` entry means "the transliterated
  algorithm satisfies the specification"; it becomes a statement about Go
  only through (i)–(iv), and `docs/semantic-boundary.md` A4 explains that
  compiler intrinsics bypass the transliterated code anyway.
* **Toolchains**: Lean 4.35.0 and Go 1.25.5, pinned.

## Counterexample workflow in detail

1. `bv_decide` fails with `The prover found a counterexample, consider the
   following assignment: x = N#w …`.
2. `scripts/mutation_test.py` (or a human, for a real finding) turns the
   assignment into a Go test with concrete inputs and the oracle from the
   manifest. The generated file names its Lean source and theorem.
3. The test is run against the real standard-library function. Outcomes:
   * real function agrees with the oracle → the *model* is wrong
     (`model_mismatch`) or the *spec* is wrong (`specification_ambiguity`);
   * real function disagrees → `go_discrepancy_reproduced`, then a
     known-issue search; `known_issue` if it matches a golang/go issue;
     otherwise a `findings/<id>/` directory is created and the result
     awaits human review. **No upstream report is filed by the pipeline.**
4. Refutations that stay (negative controls, known issues) are recorded as
   kernel-checked theorems of the negated statement (e.g.
   `Add64_nopre_refuted`), so that the audit also covers them.

## Agent roles used in this iteration

| Role | What it did here | Independence |
|---|---|---|
| Research agents (×2) | prior-art, Go testing infrastructure, known issues | fresh context; reports treated as data |
| Modelling / proof agent | this session: models, specs, proofs | its first models were wrong (precedence); the proofs rejected them |
| Adversarial reviewer | a fresh agent (no access to this session's reasoning) was told to *falsify* the `math/bits` model: it re-parsed every function, built a pure-Go copy of `bits.go` (no intrinsics), ran 9,051,590 differential vectors against the Lean model and probed the four deliberate deviations; report in `review/bits-model-review.md` (no mismatch; specification gaps found and since addressed: `Rem64` no-overflow, `Div32` quotient fit) | independent context; mechanical evidence |
| Go validation | `go/tests`, vectors, `mutation_test.py`; executed with the pinned toolchain | mechanical |
| Integration | `scripts/check.sh`, CI, manifest validator, audit | mechanical |

## Running untrusted reproducers

Generated reproducers only call pure functions of `math/bits` and the
in-repo `reference` package, with no I/O. CI runs them inside the GitHub
Actions runner with no secrets exposed. For reproducers derived from
untrusted sources, run `go test` inside a container with `--network none`
and a CPU/memory limit; the scripts never need network access.
